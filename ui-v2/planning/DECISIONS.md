# UI decisions

Record decisions that should survive across sessions.

Avoid recording every small tweak. This is for durable direction such as navigation model, density, typography choices, component conventions, and explicitly approved patterns.

## Confirmed

- UI v2 is an isolated Vue 3 + Vite application using Nuxt UI v4.
- Nuxt framework itself is not being introduced for this rebuild.
- Visual design happens before backend integration.
- Fixture/local data is acceptable during design.
- The existing production UI remains untouched until final replacement.
- `/design` is the working surface for establishing Stashd's visual language.

### Visual foundation (approved to carry into page work)

These are the directions we are now building real pages on top of. Exact numeric values (OKLCH shades, spacing scale, etc.) are implementation, not the decision, and can still be tuned without revisiting the direction itself.

- **Colour is a direct port of the legacy production palette**, not a new invention. Source: repo root `src/main.entrypoint.css` (`--color-espresso/panel/panel-raised/line/cream/muted/amber/amber-dim/success/warn/error`). Converted to oklch and mapped onto Nuxt UI's semantic tokens in `ui-v2/src/assets/css/main.css` — surfaces (`--ui-bg`/`-muted`/`-elevated`/`-accented`, `--ui-border*`) and text (`--ui-text*`) set directly from the real legacy hex rather than derived from a generic neutral ramp; `primary`/`success`/`warning`/`error` 50-950 ramps each anchor their 400 (and, for primary, 600) shade at the exact legacy value and interpolate/extrapolate the rest. UI-v2's structure/density/typography/components are the new design — only the colour character is legacy. Full mapping table lives in the commit history of `main.css`; do not re-derive these values from memory, re-read the legacy source file if they need revisiting.
- **Surfaces**: flat, subtle borders, no drop shadows. Legacy only provides four real lightness steps (page/panel/panel-raised/line) — object-level containers use `border`/`divide` for their boundary rather than a dedicated background fill; a warm surface is reserved for small, meaningful insets only (see "Chocolate is an accent" below).
- **Typography**: IBM Plex Sans + IBM Plex Mono, self-hosted. Substantially mono-forward — mono is used for identity/content whose origin traces back to an Input or source (titles, names, IDs, paths, nav labels); sans is for Stashd-authored prose and explanatory copy.
- **Navigation**: compact top bar, not a persistent sidebar. Primary destinations (Stashes, Inputs, Vault) horizontal; secondary/configuration destinations (Connections, Secrets, Settings) grouped behind a "Configure" menu; Design kept visually secondary. Broadcasts is intentionally omitted from top-level nav — where it lives contextually is still undecided. Mobile uses a drawer with all destinations reachable, no persistent sidebar, no hover dependency.
- **Phone support is first-class**, not a follow-up pass — every visually-complete slice is checked at desktop and ~390px as part of being "done."
- **Status indicators** are a quiet dot + label, never a badge/pill — deliberately lower-emphasis and non-interactive-looking, in clear contrast to real buttons. Status meaning must not rely on colour alone: the dot leads, followed by a visible lowercase text label (`active`/`paused`/`needs attention`), and the label itself is coloured to match the dot (`text-success`/`text-dimmed`/`text-error`) rather than staying a flat dimmed tone. Applies consistently to Stash, Input, and Broadcast summaries.
- **Stash detail information architecture** (superseded an earlier flatter layout after a 3-concept exploration — see git history of `StashDetailConceptsPage.vue` for the rejected alternatives): Stash identity (mono, large) stands alone; status sits directly beneath it as its own line, not inline on the title baseline; a secondary text line carries item count/size/updated. Section headings (`Inputs`, `Broadcasts`) are title-case IBM Plex Sans, visibly stronger than metadata but subordinate to the Stash title, paired with a quiet mono count and a right-aligned section-creation action. Inputs stay deliberately simple/compact — one row: icon, mono identity, status, provider/checked line, exposed Sync action, overflow. Broadcasts are intentionally richer than Inputs: an identity/status/action row, then a visually distinct inset (`bg-elevated`) operational region holding **structured, labeled facts** (not a joined metadata sentence) — fields are kind-specific (a podcast exposes Format/Published/Size/Rebuilt; a media-server broadcast adds Destination). On phone the fact region becomes a stacked key/value list rather than a two-column tile grid, so an odd number of facts never orphans a cell. The podcast feed URL keeps its own nested `bg-accented` strip with obvious Copy/Open actions and a quiet privacy hint, always visible (never behind a disclosure).
- **Corner radii** were pulled down one step app-wide for a tighter, more mechanical feel: Tailwind's `rounded-md` (used for nearly all containers/rows/insets/icon tiles) and Nuxt UI's own `--ui-radius` (buttons, dropdowns, form controls) both now render at what used to be the smaller `rounded-sm` size. Set once via `--radius-md`/`--ui-radius` in `main.css`, not per-component.
- **Chocolate is an accent, not a fill.** Two attempts at filling a whole contained-object surface (an Input/Broadcast list container) with a warm chocolate tone both read as "a brown card," no matter how far the chroma was pulled back. Object boundaries come from `border`/`divide` plus the neutral `bg-muted`/`bg-elevated` ladder — not a dedicated warm background. The one warm surface reserved for small, meaningful insets nested *inside* an object (currently: the podcast feed URL box) is Nuxt UI's own `bg-accented` token — no bespoke CSS variable needed once surfaces were ported from the legacy palette, since legacy's `line` tone naturally became `--ui-bg-accented`. Hierarchy is page → object (border-defined) → warm inset (`bg-accented`, the one accent).
- **Amber discipline**: amber communicates priority/identity/active-state, not "this is clickable" or "this creates something." Section-level creation actions (Add input, New broadcast) and frequent row actions (Sync now, Rebuild, Copy, Open feed) are neutral (`variant="subtle"`/`"soft"`/`"ghost"` + `color="neutral"`). A page is allowed to have zero amber buttons — amber still shows up via the `stashd_` underscore, active nav, progress bars, and focus/selection states. Reserve solid/soft amber for the one genuinely primary action in a context (e.g. "New stash" on the Stashes overview).
- **Action hierarchy**: a row's plausible primary reason-to-visit actions (Sync now, Rebuild, Copy, Open feed) are exposed directly as labeled buttons; secondary/destructive/rare actions (Remove, Rotate feed URL, Reconfigure destination) stay in the `⋮` overflow menu. Established on the Stash detail Inputs/Broadcasts sections.
- **Composite operation progress**: the **bar** always represents aggregate progress across the whole operation; the **stage** text names the specific item/subtask currently contributing to that aggregate and is not a second progress measurement (e.g. "Rebuilding podcast broadcast — 63%" with stage "Transcoding · Restoring a Commodore SX-64" and count "14 of 22 items"). Implemented as `src/components/OperationProgress.vue` with `default` (fuller bar, for a standalone operation) and `compact` (thin, dense, for a row/list) variants sharing one color/status system (`active`/`complete`/`queued`/`failed`) — not yet wired to any real operation.
- **Container width**: prose/forms/detail content uses a constrained reading measure (`max-w-3xl`); operational data (tables, lists) may use a wider application measure so it isn't artificially truncated or forced into horizontal scroll on ordinary desktop widths.
- **New stash workflow is source-first**, not a "create a Stash record" form: the pasted source URL is the first field, drives a locally-simulated provider/name suggestion, and the Stash name is prefillable-but-editable rather than required up front. A dedicated page (`/stashes/new`), not a modal/slideover — a form with a source field, name, sync-mode choice, and an optional advanced disclosure is enough content that a full page avoids mobile-keyboard/viewport cramping a modal would introduce. Broadcasts are explicitly out of the creation flow; the page only leaves a quiet one-line note that they can be added afterward from Stash detail. One Input only — multi-Input creation is deferred, additional Inputs are added later from Stash detail.
- **Add Input is a modal** (`UModal` from the Stash detail page), not a page — small enough content (a source field plus an optional filters disclosure) that a full-page context switch would be overkill; contrast with New Stash/New Broadcast, which are pages because their content is substantially larger. Filters mirror the real domain (`StashInputOptions`/`StashInputFilter` in the PHP app): universal title-regex include/exclude, plus YouTube-channel-only boolean options (Include Shorts / Include live), shown only when that provider is detected — filters are optional and collapsed by default, never required to add a normal Input.
- **New broadcast workflow is type-first, not taxonomy-fixed**: available Broadcast types render from a small fixture list (`availableBroadcastTypes` in `BroadcastCreatePage.vue`) rather than the page hardcoding "Podcast or Media Server" — the list today has 3 entries (Podcast, Jellyfin, Plex), mirroring the PHP app's real plugin registry (`PodcastBroadcastPlugin`/`JellyfinBroadcastPlugin`/`PlexBroadcastPlugin`), and is meant to grow without restructuring the page. Each descriptor points at one of two config sections (`configComponent: 'podcast' | 'media-server'`) — Jellyfin and Plex are separate selectable types (separate real plugins/outputs) that happen to share one config section because their settings genuinely are the same shape (connection + library + captions). Podcast and media-server configuration are intentionally NOT symmetrical: no fabricated common "destination"/"format" field forced onto both. A dedicated page (`/stashes/:stashId/broadcasts/new`), same reasoning as New Stash. Feed URLs/tokens are never generated at creation time — those come from an actual build, matching real Stashd behavior.
- **Creation Preflight** ("Preflight" is the internal name only — never shown to users; the surface reads "What Stashd will do"): before committing a creation/configuration workflow where storage/materialization is meaningful, Stashd previews estimated additional storage and aggregate planned operations, derived from the current configuration. Implemented once as `src/components/PreflightSummary.vue` + `src/types/preflight.ts` (`PreflightState`/`PreflightPlan`/`PreflightOperation`/`StorageEstimate`), reused as-is by both Add Input and New Broadcast — the component knows nothing about hardlink/transcode/download/Input/Broadcast; it only renders whatever aggregate operation rows and storage-estimate shape it's given, so a future operation kind or workflow needs no component change. Key rules: (1) Preflight never blocks creation — a valid configuration can commit before analysis finishes; the primary action's label changes to "Create without estimate" / "Add without estimate" while the storage estimate is still resolving, with a quiet caption explaining why, then reverts once ready; (2) results are partial-first — item/operation counts typically resolve before the (potentially much slower) storage estimate, and the surface shows both stages rather than one blocking spinner; (3) `StorageEstimate` is a tagged union (`none`/`estimate`/`range`/`calculating`/`unavailable`) specifically so "No additional storage" and "Unable to estimate" each get honest, non-alarming wording instead of a fake `0 B` or an error state; (4) changing configuration that affects the plan re-runs the fixture analysis and the previous result is discarded (never shown as if current) — each workflow's analysis function captures a snapshot of the relevant fields and checks it's still current before applying a delayed result, so a fast edit followed by a slower one can't have the earlier timer overwrite the later one. Do not read the fixture arithmetic in `BroadcastCreatePage.vue`/`StashDetailPage.vue` (ratios, per-item GB, timer durations) as real backend behavior — it exists only to make the interaction reviewable.
- **Vault overview is the archive-wide canonical Item inventory, not another Stashes view.** A Stash answers "what have I asked Stashd to preserve, and how have I organized it"; the Vault answers "what has Stashd actually preserved" — one row per canonical Item regardless of how many Stashes reference it or Broadcasts use it (`VaultItemFixture.stashIds`/`broadcastCount` are quiet context, never a reason to duplicate the row — `stashIds` is real membership, used for both the quiet "N stashes" hint and the Stash filter). Subtitle is fixed as "Everything Stashd has preserved." — no explanatory paragraph. `VaultItemType`/`VaultSourceFamily` (`src/types/vaultItem.ts`) are deliberately open unions, not a fixed audiovisual taxonomy — the fixture set intentionally mixes video/audio/document/photo/disc-capture so the page can't quietly assume "Item = playable media." Thumbnails are for *recognition*, not consumption: real artwork (`art`) renders as a small gradient tile, its absence falls back to a plain `bg-elevated` tile with a type icon (e.g. a PDF never looks like a broken video row) — never a play-button-first, Netflix-shelf treatment. Row click always points at the future canonical Item record (`/vault/:itemId`, currently a placeholder shell). "Preserved" is an absolute date (when Stashd acquired the Item), deliberately not a relative timestamp — relative stays reserved for operational concepts (checked/synced/rebuilt). Sort is a fixed "recently preserved first," no sort UI.
- **Vault overview leaves room for future integrity/provenance without designing it now.** The row/column shape reserves natural homes for what's coming: a `status`-shaped field can sit beside the existing quiet dot+text convention already used everywhere else (Verified/Verification due/Verifying/Missing/etc.) without restructuring the row; "Preserved" already occupies the *acquisition* date slot, leaving a distinct slot open for a future "last verified" fact; and the Item/Asset split in the real domain (`MediaItemRecord` + role-tagged `AssetRecord`s) means the future canonical Item page — not this overview — is where per-Asset integrity, provenance, and preservation history naturally belong. No fixture integrity state was invented to fill a column now.
- **Desktop table surface** (established on Vault, applied to Stash detail's Items table): a genuine desktop data table lives on ONE continuous, subtly elevated surface — `rounded-md border border-default bg-muted` wrapping the `<UTable>` — rather than sitting directly on the page background. Rows stay divided within that surface (`tbody: 'divide-y divide-default/60'`) and never become individual cards; the header row gets a faint `bg-elevated/60` tint to read as integrated rather than floating. Applies to genuine desktop tables specifically — the mobile fallback (a `divide-y`/card row list, or a `RouterLink`-wrapped row list when the table itself is clickable) is a separate, already-established pattern and is untouched by this rule.
- **Vault filter hierarchy**: `Search` (full-width, dominant) → `Type` and `Source` (always-visible selects/pickers, since both are frequent) → `Filters` (a `UPopover`, extensible home for lower-frequency facets — currently Stash membership and a Preserved date range, showing a quiet `Filters · N` count when active). **Source is hierarchical and searchable**: one `UDropdownMenu` whose `items` nest specific sources under family headers (`children`) with the component's own built-in `filter` search doing the "type to jump to a nested item" work — no custom tree-select was built. Each family's children start with an explicit "All <Family>" entry so selecting the *family* (not just a leaf source) has an unambiguous, discoverable affordance, since a menu item with `children` opens a submenu rather than being selectable itself. The closed trigger shows only the current leaf value (`Source` / `YouTube` / `@criticalrole`), never a breadcrumb string. The result summary line reflects the active filter set (`"3 of 9 items · 7.4 GB"` vs. the unfiltered `"9 items · 26.3 GB preserved"`) using simple fixture-only size-string parsing — not real Asset aggregation.
- **Status purpose** (`src/pages/StatusPage.vue`, live at `/status`; `/design/status-concept` now keeps only a small Resources specimen): Status answers three questions — "Is Stashd okay?", "What is Stashd doing?", "What is Stashd doing to my machine?" — as a compact **operational briefing**, deliberately not a generic homelab-monitoring dashboard (no Grafana/TrueNAS/Docker/`htop` replacement, no CPU-history graphs, no SMART data, no metric-card grids). Four regions, top-to-bottom by urgency: **Needs attention** (triage only — points at the owning object, does not host remediation), **In progress** (reuses `OperationProgress` as-is, one plain `bg-muted` row per operation, never a card), **Resources** (Stashd's footprint specifically, not host monitoring), **Recent** (a short operational tail — "14 items preserved," not a full audit log or internal job/queue terminology). Sections collapse when empty rather than reserving space for symmetry: "In progress" is omitted entirely when nothing is running; the healthy "Needs attention" case is one quiet dot+text line, never a success banner. **A resource condition that needs user action (e.g. storage running low) must appear in Needs attention too, not only in Resources** — Needs attention is triage, Resources is the supporting diagnosis/evidence for the same fact; normal high CPU/memory during real work is never promoted to Needs attention on its own. Needs attention (when issues exist) and Resources both get the page's bordered/elevated surface treatment — but Resources is now ONE consolidated instrument-like panel (Storage on top with capacity bar + semantic breakdown, one internal divider, then compact CPU/Memory beneath), not three separate dashboard widgets. The real page defaults to the quiet/healthy scenario; a small unobtrusive text-link scenario toggle in the header exists for reviewing all three states without a giant selector aimed at ordinary users.
- **Resources describe Stashd's impact, not the host.** Storage should reflect capacity *available to Stashd* (e.g. a 3 TB mounted quota on a 30 TB host, not the host's 30 TB) — CPU/memory should similarly reflect container/cgroup limits once real backend support exists; none of this is implemented yet, fixture data only models the intended semantics. **Storage categories carry semantic consequence**, not just directory names: Vault → *preserved* (durable), Broadcasts → *rebuildable* (generated, regenerable), Cache/temporary → *reclaimable* (ephemeral, safe to clear) — this answers "if I need space, what can safely go?" without implying the three categories are equally disposable. High resource utilization is informative, not automatically alarming: 78% CPU during active transcoding gets plain neutral typography and a contextual explanation ("Transcoding 4 items"), not warning/error color — color is reserved for conditions Stashd actually knows are a problem (e.g. a storage-pressure note), never applied automatically from a threshold, and meaning must never depend on color alone.
- **Primary navigation is now Status · Stashes · Vault** (`Configure` unchanged), replacing `Stashes · Inputs · Vault`. Conceptually: Status = "is Stashd okay, what's it doing, what's it consuming"; Stashes = "what have I asked Stashd to preserve, and how is it organized"; Vault = "what has Stashd actually preserved"; Configure = "how is Stashd set up." **Inputs and Broadcasts are contextual to Stashes, not primary global destinations** — Input/Broadcast functionality, routes, and UI are all untouched (Add Input, the Stash-detail Inputs/Broadcasts sections, and the standalone `/inputs` route all still exist); only `Inputs`' presence in primary nav (desktop `UNavigationMenu` and the mobile drawer, which share the same `primaryLinks` array in `App.vue`) was removed. Two open questions, deliberately not resolved here: whether the standalone `/inputs` route still earns a home somewhere (e.g. cross-Stash troubleshooting tooling) now that it's not in primary nav, and whether Status should eventually become the app's default landing route (currently `/` still redirects to `/stashes`, and the `stashd_` wordmark still links to `/`) — both are later IA decisions.
- **Operational ownership**: Status surfaces and prioritizes operational facts; it does not own remediation. A failed Broadcast rebuild routes toward the Stash/Broadcast that owns it, a connection issue toward Configure/Connections, a future integrity problem toward the Vault Item preservation record — Status is the triage layer, domain pages own the underlying objects and any fix.
- **Preservation confidence is a primary user-facing property of a canonical Vault Item.** The Vault overview answers "what has Stashd actually preserved"; the canonical Item page (`src/pages/VaultItemPage.vue`, live at `/vault/:itemId`, fixture-backed via `src/fixtures/vaultItemRecords.ts` + `src/types/preservationRecord.ts`) answers "can I trust this preserved thing, and what exactly does Stashd have for it." Integrity/fixity technically exists at the Asset level, but the Item page derives and prominently surfaces one Item-level **Preservation status** — the first substantive section, before Assets, before provenance, before anything else — using the same quiet dot + visible-text convention as the rest of the app, just at slightly larger emphasis (`size-2` dot, `text-sm` label) since it's the page's headline fact. Deliberately named "Preservation status," not "Safe"/"Verified ✓" as a standalone claim: `Verified` means the relevant durable Assets currently match their recorded fixity data — it does NOT mean backed up, redundant, or protected from future loss. Never use "safe," "protected," or "guaranteed" in this copy. **`Verified`/"last verified" must only describe a successful verification, never merely an attempt** — `PreservationStatus` carries `lastVerifiedLabel` (last success) and `lastMismatchLabel` (last failed attempt) as two separate optional facts specifically so a failed check is never worded as if it were a success (e.g. Field Log 14 shows both "Last verified 2 Aug 2026" and, in error tone, "Mismatch detected 7 Aug 2026" — never "Last verified 7 Aug 2026" for a date the check actually failed). **Source availability is a separate, distinct fact from preservation state** — a gone upstream (e.g. a deleted YouTube video) is not an integrity failure and must never be presented in error styling; it renders with a neutral dot in its own labeled sub-block, demonstrating Stashd's actual success case ("upstream gone, preserved copy verified"). The page deliberately has only one bordered/elevated surface (Preservation status); Assets are plain `bg-muted` rows one tier down, and Provenance/Organised in/Used by/History are plain text with no surface at all — a deliberate three-tier weighting (elevated > filled row > plain text) so lower-priority sections don't visually compete with the two that matter. Assets communicate **role** (Original/Preservation master/Extracted text/…) before filename, and note `derived from <asset>` when applicable — this is not an Asset inspector, no codec/checksum/path detail belongs here (that's a future Asset detail page). "Organised in" (Stashes) and "Used by" (Broadcasts) are relationships around the canonical Item, not ownership — no edit controls; an empty "Used by" is common (most Items aren't used by any Broadcast) so that section is omitted entirely rather than shown as an empty state — this does not generalize to "Organised in" or any other relationship without a deliberate decision. History is a short (max 3), restrained date+label list with a top rule and internal dividers — quieter than Assets, but structured enough to read as evidence, not footer text. The layout intentionally does not assume every Item has a thumbnail, duration, creator, single Asset, or identical provenance shape — provenance is a flexible intro line plus an optional small fact list, not a fixed grid. Only 4 of the 9 Vault overview Items have a full record (Exhibit 103/`vault-4`, Blade Runner/`vault-5`, The Sunken Archive/`vault-1`, Field Log 14/`vault-7`) — an overview row without one still opens to identity + a plain "a full preservation record isn't available yet" line rather than a dead end. `/design/vault-item-concept` was simplified to a small Preservation Status specimen once the real route existed — it is no longer the full page mockup.

Spacing scale and the mono/sans boundary for borderline cases are also still open.

- Which page is designed first after the visual language is established.
- Whether Broadcasts needs its own top-level or contextual entry point.

- **Known polish issue (not yet fixed):** open dropdown/select popover surfaces (`UDropdownMenu`, `USelect`, etc.) can be hard to distinguish from the page background — their surface colour is too close to `bg-default`/`bg-muted`. Noticed while building the New Broadcast/Add Input forms; needs a deliberate elevated-surface pass across all overlay/popover components, not a one-off fix.
